# 长对话实际读屏链路修复

源码版本：`2026-11-02.screen-voice.1`。

## 故障证据

用户本次实际对话中两次问“看得见屏幕吗”，助手都答“目前还没有看到屏幕画面，可能需要先开启屏幕共享”。该实例共享记录显示曾采集62帧、完成4次视觉分析且没有分析错误。因此，上次以采集/分析计数通过来判断用户可用，是不充分的验收。

代码中的实际断点是：共享结果原来只在进入执行任务时放入交接上下文；`AgentRealtimeVoice` 没有画面状态提供器，也没有向实时会话发送画面资料。普通语音回答可能完全不调用执行器，导致听说模型没有画面可依据。上次只改了说明和入口，没有接通这条数据链。

## 修复

- 创建智能体实时通话时，在连接之前绑定 `screen_context_provider`。初次 `session.update` 已含共享实际状态、前台身份及画面摘要。
- 通话工作线程持续检查画面资料。内容或有效性改变时用 `session.update.instructions` 替换当前资料；不伪造用户消息，不主动请求说话，不为每一采集帧发送更新。实际发送与服务端确认次数在 `app_state.screen_share.voice_bridge` 可见。
- 实时模型新增 `read_screen(question)`。摘要未就绪、过期或细节不足时，通过Qt信号在后台读取最新共享帧并按问题识别，再返回实际语音工具结果；无需把画面问题启动成电脑执行任务。
- 执行模型获得本轮共享的最新图帧；问答分支也获得共享资料与最新图帧。用户不需要手动附截图。
- 统一说明：共享已开但资料未就绪时应调用读屏工具，不能把没有原生视频输入误称为没有共享能力，也不能反复让用户开启共享。
- 不显示预览，仍保持长通话默认启停；普通任务不会自行开共享。手动停止共享后，新状态会进入语音会话。
- 沿用现有千问模型和已确认的赠送额度保护，没有改成付费视频模型。

## 验收边界

90项相关回归通过，涵盖实际通话入口绑定、初始会话资料、静默更新、服务端确认计数、画面变化、手动停止、直接读屏信号与宿主执行路径、问答和原语音协议。代码编译与差异空白检查通过。动画文件关闭的既有ResourceWarning仍在。

真实视觉服务及真实千问语音服务验证，使用程序渲染的两组固定测试帧作为采样输入，未使用麦克风或播放设备：

1. 蓝色圆形、黄色方形：实际语音文本正确识别两种颜色与形状。严格标题断言没有通过，因为回答使用了真实提供的原生窗口标题“咕嘎屏幕连接验收”，而测试期待页面大字“海风读书角”。
2. 换为绿色三角形、红色圆形：实际语音正确说出新图形和页面标题“星河音乐站”。

该轮21.31秒，实时会话资料更新3次，服务端确认3次，无服务端错误。画面识别与切换链路已有真实服务证据；**严格的标题断言并未全部通过，不能称整轮全通过**。证据保留在 `runtime/screen-voice-qa/real-bridge.json`。

前两次桌面测试受到其他窗口遮挡，未形成固定目标的有效验收；已停止这些有界测试。后续改为固定渲染帧，以隔离桌面干扰。临时诊断截图已删除。固定帧验证不能代替真实麦克风和实际桌面遮挡场景的全面验收。
