# dsh-layerfs 对咕嘎多智能体的适配调研（2026-10-29）

## 结论

有价值，最适合补齐“真正并行开发、各自修改、可追踪合并和独立验收”。它不直接提供桌面操作、人格记忆或更强的模型。建议先补咕嘎的任务调度与成果验收，再以可替换的工作区后端评估接入 LayerFS。

本轮为资料与现有代码核对，没有部署该插件或修改运行中的 DSH 配置。

## 已核对的上游事实

1. dsh-layerfs 是社区组织 Ephemeral-AI-Lab 的 DSH 插件，不是 DSH 自身的新版本。插件由 Host 和客户端组成，提供工作与历史视图，接入 LayerFS 的分支、工作区、提交、合并和发布。来源：https://github.com/Ephemeral-AI-Lab/dsh-layerfs
2. 当前 package.json 标记插件 0.1.0，要求 DSH >=0.2.1-alpha.4 且 <0.3.0；layerfs.json 绑定具体上游提交。不能直接把任意 latest 版本组合起来。来源：https://raw.githubusercontent.com/Ephemeral-AI-Lab/dsh-layerfs/main/packages/dsh-layerfs/package.json
3. 官方文档主要检查 dsh web；desktop 未经其验证；headless 不提供预设注册，但 Host 与 bash 环境仍可以加载。不能简单说 headless 完全不支持，也不能把完整 web 方案当成当前 sidecar 可直接替换的组件。来源：https://layerfs.ai/docs/integrations/dsh/
4. Windows 的 Store 操作由 WSL2 中的 Linux worker 完成，Store 要在 Linux 本地文件系统，执行环境需要 Docker；不是把 Store 放在 C 盘后原生运行。当前 Disposable 模式也不承诺断电持久性，仍需要 Git 等外部持久备份。来源：https://layerfs.ai/docs/platform/
5. 历史保存的是文件状态，不包含运行中的进程、内存或外部软件状态。publish 不会自动把分支落后期间的主线改动合并回来；应先同步、合并、验证，再发布。来源：https://layerfs.ai/docs/concepts/

上游演示中的多智能体完成率、耗时和存储压缩结果是项目方报告，本机没有复现实测，不能据此承诺咕嘎提速比例。

## 本机核对

- 实际 dsh --version：0.1.7-rc.2，低于插件当前要求。
- Node：可执行文件为 node-v24.19.0-win-x64，可满足 README 给出的 Node 版本门槛。
- wsl --list --quiet：仅返回 docker-desktop。本轮未启动发行版或安装新的 Linux 系统。
- docker version：无法连接 dockerDesktopLinuxEngine 命名管道，当前未取得可用 Docker 服务。
- 没有下载大体积依赖、编译 LayerFS、修改全局 DSH profile。

## 咕嘎当前真实能力与缺口

- core/agent_memory.py：已有独立成员档案、人格、音色、对话和长期记忆。
- ui/multi_agent_window.py：是独立桌宠窗口与团队控制器，本身不是每人独立的任务执行进程。
- core/agent_council.py：成员按顺序调用模型讨论，不带执行工具，也不自动将讨论结果变成操作。
- ui/agent_chat.py：一个共享执行面板；忙碌或实时通话时限制切换其他成员。
- core/dsh_worker.py：一个 DshManager 一次接受一个外部任务，使用 --profile headless。完成判断依赖正常退出、无错误、存在 final_text；这不等于独立验证成品。
- core/agent_task.py 与 core/self_agent.py：任务临时目录已分开，但操作现有项目仍可指向同一个目录。临时目录不是权限隔离，也不是受控分支合并。
- core/execution_contract.py：已有部分工具回执与操作复查，适合扩展为跨成员的统一结果协议，无需全部重写。

## 推荐的内核结构（设计建议，尚未实施）

1. 用户目标交给咕嘎总调度，生成带验收要求的小任务。
2. Dora、大肥鱼各有独立任务实例、工作区、取消信号、预算和事件流；人格与业务角色分开，不限制通用工具能力。
3. 不同成员可并行读资料、编写不同模块、运行各自的测试。每位成员在自己的工作区顺序执行步骤。
4. 同一 Windows 桌面的鼠标、焦点、剪贴板和麦克风统一排队；不能把多个代码分支误当成多个独立桌面。
5. 成果提交包含：修改清单、实际文件、验证命令、退出码、必要截图、失败与未解决项。先由程序验收，再由咕嘎汇总。
6. 同步最新主线，合并候选成果，在合并后的状态上测试，通过才更新正式运行版。失败保留候选成果，不直接污染当前桌宠。
7. 私有长期记忆继续按成员隔离；新增“项目共享事实”只接收有依据的结论，不合并所有聊天。
8. 前台仍隐藏逐工具流水账，只展示结果、必要进度和需要用户决定的事项；完整追踪放到可展开的开发面板。

## 分阶段优先级

P0：先补独立成果验收。重点堵住“子进程退出并说完成，就宣称任务完成”的缺口。

P1：新增任务池与独立工作区。先限制为两名后台成员，并用现有 Git 独立工作副本实现文件层分开；清楚标注这不是权限沙箱。保留桌面执行队列。

P2：验证一个可重复的协作开发任务。例如 Dora 制作待办工具界面，大肥鱼完成数据保存与测试，咕嘎合并。验收需要两个任务时间有重叠、无文件互相覆盖、合并后应用可启动并保存数据、停止一个子任务不会误杀其他成员、失败能明确报告并保留正式版。

P3：在独立测试环境验证新 DSH + LayerFS 的精确版本组合。确认 Windows worker、真实工作区及 headless 适配可用后，再替换工作区后端。语音、人格、记忆和桌宠外观保持现有实现。

## 能带来的提升边界

能改善：多人改文件互相覆盖、长任务难追踪、失败难恢复、成果无法归因、并行开发没有统一汇总。

需要咕嘎自己补：任务拆分、调度、独立验收、共享事实、桌面互斥、语音进度汇报。

不能由文件快照撤回：已发送的微信消息、已经在网页提交的内容、鼠标已造成的外部结果、运行中的游戏或应用内存。文件合并成功也不保证程序逻辑正确。
